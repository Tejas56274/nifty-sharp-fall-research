## 3. Which important decisions did I make myself? `[YOUR INPUT]`

I chose the core research framing and the concrete defaults that drive the prototype:

* **Sharp‑fall definition** – a single‑day close‑to‑close decline (default ≤ ‑2%). I deliberately avoided a multi‑day drawdown definition to keep the experiment simple and aligned with a typical lay interpretation.
* **Entry timing** – buying at the *next* day’s close, which eliminates look‑ahead bias that would arise if we entered on the same day as the fall.
* **Holding period** – a default of 10 trading days, editable by the user, providing a reasonable short‑term horizon while keeping the sample size manageable.
* **Cost model** – a flat round‑trip cost of 10 bps, shown as an editable control, acknowledging that real‑world slippage is higher on volatile days but keeping the prototype lightweight.
* **User‑first UI** – exposing every assumption (threshold, holding period, costs, etc.) before the experiment runs, so nothing is hidden from the user.
* **Result presentation** – separating raw numbers (“what the data shows”) from an interpretation (“what the system concludes”), clearly labeling the latter as an opinion, not a fact.

These choices shape the entire workflow and were made deliberately rather than being generated by the AI.

## 4. Did I reject or modify any AI‑generated suggestions? Why? `[YOUR INPUT]`

Yes. The AI initially suggested pulling live NIFTY data via an external API and building a more elaborate dashboard with multiple charts and a backend. I rejected those ideas because:

* **Reproducibility** – a seeded simulated price series guarantees that anyone can run the prototype and obtain identical results without needing API keys or dealing with data licensing.
* **Scope** – the assignment focuses on the research workflow, not on data engineering or UI polish. Adding a backend would introduce unnecessary complexity and distract from the core learning objectives.
* **Deployment simplicity** – a single static HTML file can be opened locally or hosted on any static site platform with zero configuration, which aligns with the “no‑install‑needed” promise in the README.
* **Time constraints** – implementing a full data pipeline would consume the limited development time that could be better spent on making the assumptions explicit and the interpretation transparent.

I kept the AI‑generated core logic for the simulator and the canvas visualisations because they were well‑implemented and served the purpose.

## 5. What part of the solution am I most proud of? `[YOUR INPUT]`

I am most proud of the **transparent assumption handling**. The Clarify step surfaces every assumption—threshold, holding period, entry timing, costs—as editable controls before any back‑test runs. This forces the user to confront the hidden decisions that normally lurk in trading‑strategy backtests. Coupled with the explicit split between “what the data shows” and the system’s interpretation, the prototype makes it clear where the evidence ends and the analyst’s judgment begins, which is exactly the research‑mindset the project set out to demonstrate.
